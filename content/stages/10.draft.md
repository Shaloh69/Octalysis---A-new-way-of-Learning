<!-- block: brief -->
Stage 09 settled how numbers live in bits and how the ALU works on them. This
stage asks what the processor is **told** to do with them. The instruction set
is the one place where the hardware designer and the programmer look at the same
machine: the designer has to build every instruction in it, and the programmer
can use nothing outside it.

You will take an instruction apart into its elements, see why the number of
addresses in an instruction is a real design trade-off, sort the data an
instruction can operate on, survey the kinds of operation every machine offers,
and finish with the question of which end of a word is stored first.

<!-- block: callout -->
**8086 assembly is assumed knowledge.** It comes from your Microprocessors
prerequisite. This chapter uses x86 and ARM as examples of design choices, not to
teach you to program them.

<!-- block: prose -->
## What a machine instruction is

<!-- block: quote source="ch-12.md 12.1" -->
The operation of the processor is determined by the instructions it executes, referred to as machine instructions or computer instructions. The collection of different instructions that the processor can execute is referred to as the processor’s instruction set.

<!-- block: prose -->
### The four elements

Every instruction has to tell the processor four things, though not every
instruction states all four explicitly.

**1. The operation code.**

<!-- block: quote source="ch-12.md 12.1" -->
Specifies the operation to be performed (e.g., ADD, I/O).
The operation is specified by a binary code, known as the operation code, or opcode.

<!-- block: prose -->
**2. Source operand references.**

<!-- block: quote source="ch-12.md 12.1" -->
The operation may involve one or more source operands, that is, operands that are inputs for the operation.

<!-- block: prose -->
**3. A result operand reference**, because the operation may produce a result.

**4. A next instruction reference.**

<!-- block: quote source="ch-12.md 12.1" -->
This tells the processor where to fetch the next instruction after the execution of this instruction is complete.

<!-- block: prose -->
The fourth is usually invisible:

<!-- block: quote source="ch-12.md 12.1" -->
In most cases, the next instruction to be fetched immediately follows the current instruction. In those cases, there is no explicit reference to the next instruction.

<!-- block: prose -->
### Where operands can be

A source or result operand lives in one of four places: **main or virtual
memory** (the instruction must supply an address), a **processor register** (the
instruction supplies the register's number), the instruction itself as an
**immediate** value, or an **I/O device**. Two of those deserve the book's own
words:

<!-- block: quote source="ch-12.md 12.1" -->
The value of the operand is contained in a field in the instruction being executed.

<!-- block: quote source="ch-12.md 12.1" -->
The instruction must specify the I/O module and device for the operation. If memory-mapped I/O is used, this is just another main or virtual memory address.

<!-- block: prose -->
That last sentence is Stage 07 coming back: with memory-mapped I/O, a device
register is just an address, and the instruction set needs no special case.

### Instruction representation

Inside the machine an instruction is a string of bits divided into **fields**,
one per element. The simplest example is a 16-bit format:

<!-- block: figure id="10-instruction-format" after="12.2" -->
A simple instruction format. A 4-bit opcode can name 2⁴ = 16 operations, and
each 6-bit operand reference can name 2⁶ = 64 locations.

<!-- block: prose -->
Nobody reads those bits by eye, so instructions are written symbolically:

<!-- block: quote source="ch-12.md 12.1" -->
Opcodes are represented by abbreviations, called mnemonics, that indicate the operation.

<!-- block: prose -->
Operands are written symbolically too. The book's example is `ADD R, Y`, which

<!-- block: quote source="ch-12.md 12.1" -->
may mean add the value contained in data location Y to the contents of register R. In this example, Y refers to the address of a location in memory, and R refers to a particular register. Note that the operation is performed on the contents of a location, not on its address.

<!-- block: prose -->
Keep that last sentence in mind: an operand reference names **where** a value
is, and the operation acts on **what is there**.

<!-- block: prose -->
## Instruction types

One high-level statement usually becomes several machine instructions. The
book's example is `X = X + Y`, with X and Y at memory locations 513 and 514:

<!-- block: quote source="ch-12.md 12.1" -->
1. Load a register with the contents of memory location 513.
2. Add the contents of memory location 514 to the register.
3. Store the contents of the register in memory location 513.

<!-- block: quote source="ch-12.md 12.1" -->
A high-level language expresses operations in a concise algebraic form, using variables. A machine language expresses operations in a basic form involving the movement of data to or from registers.

<!-- block: prose -->
An instruction set has to be able to express anything a high-level language
can. That requirement sorts instructions into four types:

<!-- block: callout -->
**The four instruction types** (book §12.1):

| Type | What it covers |
|---|---|
| Data processing | arithmetic and logic instructions |
| Data storage | moving data between registers and memory |
| Data movement | I/O instructions |
| Control | test and branch instructions |

<!-- block: quote source="ch-12.md 12.1" -->
Test instructions are used to test the value of a data word or the status of a computation. Branch instructions are then used to branch to a different set of instructions depending on the decision made.

<!-- block: prose -->
## Number of addresses

How many operand addresses should one instruction carry? Count what a binary
operation needs: two sources, one destination, and the next instruction. That is
four, and nobody builds that:

<!-- block: quote source="ch-12.md 12.1" -->
In most architectures, many instructions have one, two, or three operand addresses, with the address of the next instruction being implicit (obtained from the program counter).

<!-- block: prose -->
The fewer addresses an instruction carries, the more of them must be implied.
Here is the same calculation, **Z = (A + B) × C**, written four ways. (This is
our own example; the book's Figure 12.3 does the same for a longer expression.)

<!-- block: code -->
three addresses — 2 instructions
  ADD  T, A, B     T ← A + B
  MPY  Z, T, C     Z ← T × C

two addresses — 3 instructions
  MOVE Z, A        Z ← A
  ADD  Z, B        Z ← Z + B
  MPY  Z, C        Z ← Z × C

one address — 4 instructions
  LOAD A           AC ← A
  ADD  B           AC ← AC + B
  MPY  C           AC ← AC × C
  STOR Z           Z ← AC

zero addresses (stack) — 6 instructions
  PUSH A           stack: A
  PUSH B           stack: A B
  ADD              stack: A+B
  PUSH C           stack: A+B C
  MPY              stack: (A+B)×C
  POP  Z           Z ← (A+B)×C

<!-- block: prose -->
Read them bottom to top and the pattern is plain: each address you remove
makes every instruction shorter and the program longer.

- **Two-address** instructions make one operand do double duty, as source and as
  result. That is why the second column needs a `MOVE` first: without it, `ADD`
  would overwrite A.
- **One-address** instructions imply the second operand.

<!-- block: quote source="ch-12.md 12.1" -->
This was common in earlier machines, with the implied address being a processor register known as the accumulator (AC). The accumulator contains one of the operands and is used to store the result.

<!-- block: quote source="ch-12.md 12.1" -->
Zero-address instructions are applicable to a special memory organization called a stack. A stack is a last-in-first-out set of locations.

<!-- block: prose -->
A zero-address `ADD` takes the top two elements of the stack and leaves their
result on top. In the book's Table 12.1 notation that is T ← (T − 1) OP T, where
T is the top of the stack.

<!-- block: quote source="ch-12.md 12.1" -->
The number of addresses per instruction is a basic design decision. Fewer addresses per instruction result in instructions that are more primitive, requiring a less complex processor. It also results in instructions of shorter length. On the other hand, programs contain more total instructions, which in general results in longer execution times and longer, more complex programs.

<!-- block: quote source="ch-12.md 12.1" -->
Because register references are faster than memory references, this speeds up execution. For reasons of flexibility and ability to use multiple registers, most contemporary machines employ a mixture of two- and three-address instructions.

<!-- block: prose -->
## Instruction set design

The instruction set shapes the processor that implements it and is the
programmer's only handle on that processor, so its design pulls in both
directions at once. The book names five fundamental issues, and notes that they
are still argued over:

<!-- block: callout -->
**The five design issues** (book §12.1):

| Issue | The question it asks |
|---|---|
| Operation repertoire | how many operations, which ones, how complex |
| Data types | what kinds of data operations act on |
| Instruction format | instruction length, number of addresses, field sizes |
| Registers | how many registers instructions can name, and what for |
| Addressing | how an operand's address is specified (Stage 11) |

<!-- block: quote source="ch-12.md 12.1" -->
These issues are highly interrelated and must be considered together in designing an instruction set.

<!-- block: prose -->
## Types of operands

<!-- block: quote source="ch-12.md 12.2" -->
Machine instructions operate on data. The most important general categories of data are

<!-- block: prose -->
**addresses, numbers, characters, and logical data.** Addresses are data too:
an address is often computed before it is used, and for that purpose it is
treated as an unsigned integer. Stage 11 is about exactly that computation.

### Numbers

Machine numbers differ from mathematics' numbers in one important way:

<!-- block: quote source="ch-12.md 12.2" -->
First, there is a limit to the magnitude of numbers representable on a machine and second, in the case of floating-point numbers, a limit to their precision.

<!-- block: prose -->
Three numeric types are common: binary integers (fixed point), binary floating
point (both Stage 09), and **decimal**. Decimal exists because people read and
type decimal:

<!-- block: quote source="ch-12.md 12.2" -->
For applications in which there is a great deal of I/O and comparatively little, comparatively simple computation, it is preferable to store and operate on the numbers in decimal form. The most common representation for this purpose is packed decimal.

<!-- block: quote source="ch-12.md 12.2" -->
To form numbers, 4-bit codes are strung together, usually in multiples of 8 bits. Thus, the code for 246 is 0000 0010 0100 0110. This code is clearly less compact than a straight binary representation, but it avoids the conversion overhead.

<!-- block: prose -->
A sign is one more 4-bit digit at either end: the book gives **1100 for +** and
**1101 for −**. Worked through for −93, with the sign digit on the right and a
leading zero digit to fill whole bytes:

<!-- block: code -->
−93 in packed decimal
digits     0     9     3     −
codes   0000  1001  0011  1101     = 0x093D   (two bytes)
compare: +93 in 8-bit binary is 0101 1101, one byte

<!-- block: prose -->
Each 4-bit code uses only 10 of its 16 patterns, which is why packed decimal is
bigger than binary. What it buys is no decimal-to-binary conversion on input or
output.

### Characters

<!-- block: quote source="ch-12.md 12.2" -->
Today, the most commonly used character code in the International Reference Alphabet (IRA), referred to in the United States as the American Standard Code for Information Interchange (ASCII; see Appendix H). Each character in this code is represented by a unique 7-bit pattern; thus, 128 different characters can be represented.

<!-- block: prose -->
IRA characters are almost always stored in 8 bits, the eighth bit either 0 or a
parity bit. The digit characters are arranged on purpose:

<!-- block: quote source="ch-12.md 12.2" -->
This is the same code as packed decimal. This facilitates conversion between 7-bit IRA and 4-bit packed decimal representation.

<!-- block: prose -->
The digits 0 to 9 are `011 0000` to `011 1001`, so the low four bits are the
digit's packed-decimal code. IBM mainframes use a different 8-bit code,
**EBCDIC**, which is also compatible with packed decimal.

### Logical data

<!-- block: quote source="ch-12.md 12.2" -->
It is sometimes useful, however, to consider an n-bit unit as consisting of n 1-bit items of data, each item having the value 0 or 1. When data are viewed this way, they are considered to be logical data.

<!-- block: prose -->
The interesting consequence is that the bits themselves carry no type:

<!-- block: quote source="ch-12.md 12.2" -->
Note that, in the preceding examples, the same data are treated sometimes as logical and other times as numerical or text. The “type” of a unit of data is determined by the operation being performed on it.

<!-- block: prose -->
In a high-level language the compiler checks types. In machine language, the
byte `0x37` is the character `7`, the number 55, or eight flags, depending only
on which instruction touches it.

<!-- block: prose -->
## x86 and ARM data types

### x86

The x86 handles data 8 bits (byte), 16 (word), 32 (doubleword), 64 (quadword)
and 128 bits (double quadword) long, and does **not** require them to be aligned:
a doubleword may start at any address. The cost of misalignment is paid on the
bus, where transfers happen in aligned doublewords, so the processor splits a
misaligned request into several transfers.

<!-- block: quote source="ch-12.md 12.3" -->
As with all of the Intel 80x86 machines, the x86 uses the little-endian style; that is, the least significant byte is stored in the lowest address (see Appendix 12A for a discussion of endianness).

<!-- block: prose -->
Beyond those general types, specific instructions recognise more specific ones.
The book's Table 12.2 lists them; the ones you should be able to name are:

<!-- block: callout -->
**Selected x86 data types** (book Table 12.2):

| Type | Meaning |
|---|---|
| Integer | signed, two's complement |
| Ordinal | unsigned integer |
| Unpacked BCD | one decimal digit per byte |
| Packed BCD | two decimal digits per byte, 0 to 99 |
| Near pointer | an offset within a segment |
| Far pointer | a segment selector plus an offset |
| Floating point | IEEE 754 formats (Stage 09) |
| Packed SIMD | several operands packed into 64 or 128 bits |

<!-- block: quote source="ch-12.md 12.3" -->
The basic concept is that multiple operands are packed into a single referenced memory item and that these multiple operands are operated on in parallel.

<!-- block: prose -->
### ARM

<!-- block: quote source="ch-12.md 12.3" -->
ARM processors support data types of 8 (byte), 16 (halfword), and 32 (word) bits in length. Normally, halfword access should be halfword aligned and word accesses should be word aligned.

<!-- block: prose -->
Note the vocabulary clash: an ARM **word** is 32 bits, an x86 **word** is 16.
For an unaligned access ARM offers three behaviours: a default where the low
address bits are treated as zero, an **alignment fault** when checking is
switched on, or a transparent **unaligned access** using more than one memory
access. Every size can be read as unsigned or as two's complement.

<!-- block: quote source="ch-12.md 12.3" -->
The majority of ARM processor implementations do not provide floatingpoint hardware, which saves power and area.

<!-- block: prose -->
(Floating point is offered as an optional coprocessor, following IEEE 754.) ARM
can also switch endianness under program control: the `SETEND` instruction sets
or clears an **E-bit** that decides the byte order of loads and stores.

<!-- block: prose -->
## Types of operations

<!-- block: quote source="ch-12.md 12.4" -->
The number of different opcodes varies widely from machine to machine. However, the same general types of operations are found on all machines.

<!-- block: prose -->
The seven types are **data transfer, arithmetic, logical, conversion, I/O,
system control, and transfer of control.** The book's Table 12.3 lists the
common operations in each.

### Data transfer

<!-- block: quote source="ch-12.md 12.4" -->
The most fundamental type of machine instruction is the data transfer instruction.

<!-- block: prose -->
A transfer instruction must say where the source and destination are (memory,
register, or the top of the stack), how much data moves, and how each operand is
addressed. Register to register is the simple case. When memory is involved, the
processor works through the stages you already know:

<!-- block: quote source="ch-12.md 12.4" -->
1. Calculate the memory address, based on the address mode (discussed in Chapter 13).
2. If the address refers to virtual memory, translate from virtual to real memory address.
3. Determine whether the addressed item is in cache.
4. If not, issue a command to the memory module.

<!-- block: prose -->
That is Stage 11 (addressing), Stage 08 (virtual memory) and Stage 04 (cache) in
one list.

### Arithmetic

Add, subtract, multiply and divide, always for signed integers and often for
floating point and packed decimal too, plus single-operand operations such as
**absolute**, **negate**, **increment** and **decrement**. Each one moves
operands to the ALU and sets the condition codes on the way out.

### Logical

<!-- block: quote source="ch-12.md 12.4" -->
Thus, the AND operation can be used as a mask that selects certain bits in a word and zeros out the remaining bits.

<!-- block: prose -->
That is how you turn the character `7` into the number 7:

<!-- block: code -->
'7' in IRA     0011 0111
AND mask       0000 1111
result         0000 0111   = 7

<!-- block: prose -->
And XOR with all 1s inverts every bit, the one's complement. Shifts and rotates
come in three kinds:

<!-- block: quote source="ch-12.md 12.4" -->
With a logical shift, the bits of a word are shifted left or right. On one end, the bit shifted out is lost. On the other end, a 0 is shifted in.

<!-- block: quote source="ch-12.md 12.4" -->
The arithmetic shift operation treats the data as a signed integer and does not shift the sign bit. On a right arithmetic shift, the sign bit is replicated into the bit position to its right.

<!-- block: quote source="ch-12.md 12.4" -->
Rotate, or cyclic shift, operations preserve all of the bits being operated on.

<!-- block: prose -->
One input, every shift by 2 bits. (Our own example; the book's Table 12.7 does
the same with 3 bits.) The input is 1100 1000, which is −56 in two's complement:

<!-- block: code -->
input                       1100 1000      (−56)
logical right shift  2      0011 0010      (0s in from the left)
logical left shift   2      0010 0000      (0s in from the right)
arithmetic right     2      1111 0010      (−14 = −56 ÷ 4, sign copied in)
right rotate         2      0011 0010      (the 00 that fell off re-enters on the left)
left rotate          2      0010 0011      (the 11 that fell off re-enters on the right)

<!-- block: prose -->
The logical right shift and the right rotate agree here only because the two bits
that fell off were both 0. Change the input's low bits and they differ.

<!-- block: quote source="ch-12.md 12.4" -->
With numbers in twos complement notation, a right arithmetic shift corresponds to a division by 2, with truncation for odd numbers. Both an arithmetic left shift and a logical left shift correspond to a multiplication by 2 when there is no overflow.

<!-- block: prose -->
### Conversion, I/O and system control

<!-- block: quote source="ch-12.md 12.4" -->
Conversion instructions are those that change the format or operate on the format of data. An example is converting from decimal to binary.

<!-- block: prose -->
**I/O** instructions are few on most machines; Stage 07 showed why (memory-mapped
I/O, DMA, I/O processors). **System control** instructions are privileged:

<!-- block: quote source="ch-12.md 12.4" -->
System control instructions are those that can be executed only while the processor is in a certain privileged state or is executing a program in a special privileged area of memory. Typically, these instructions are reserved for the use of the operating system.

<!-- block: prose -->
That is Stage 08's kernel mode, seen from the instruction set's side.

### Transfer of control

<!-- block: quote source="ch-12.md 12.4" -->
For these instructions, the operation performed by the processor is to update the program counter to contain the address of some instruction in memory.

<!-- block: prose -->
Programs need this for three reasons: to repeat instructions in a **loop**, to
**decide** between two courses, and to break a large program into **procedures**.
Three mechanisms provide it.

**Branch (jump).** The instruction carries the address of the next instruction.

<!-- block: quote source="ch-12.md 12.4" -->
Most often, the instruction is a conditional branch instruction. That is, the branch is made (update program counter to equal address specified in operand) only if a certain condition is met. Otherwise, the next instruction in sequence is executed (increment program counter as usual).

<!-- block: prose -->
The condition usually comes from a **condition code** set by an earlier
operation, so `BRZ X` branches if the last result was zero. The alternative is a
compare-and-branch in one instruction, such as `BRE R1, R2, X`.

**Skip.** The address is implied: skip the next instruction. The book's example
is increment-and-skip-if-zero (`ISZ`), which closes a counting loop in two
instructions.

**Procedure call.** A call branches to the procedure; a return comes back to the
instruction after the call. Procedures nest, so the return address must be saved
somewhere: a register, the start of the procedure, or the stack. The stack is the
general answer, because it allows a procedure to be called again before it has
returned:

<!-- block: quote source="ch-12.md 12.4" -->
A reentrant procedure is one in which it is possible to have several calls open to it at the same time.

<!-- block: prose -->
A trace in our own numbers. MAIN calls P from address 100, and P calls Q from
address 205; each call pushes the address of the instruction after it:

<!-- block: code -->
event               stack after it (top on the right)
start               (empty)
MAIN: CALL P        101
P:    CALL Q        101  206
Q:    RETURN        101          → resumes P at 206
P:    RETURN        (empty)      → resumes MAIN at 101

<!-- block: quote source="ch-12.md 12.4" -->
The entire set of parameters, including return address, that is stored for a procedure invocation is referred to as a stack frame.

## x86 and ARM operation types

### x86: call and return, and a lesson about complexity

On entry, a procedure pushes the return point, pushes the old frame pointer,
copies the stack pointer into the frame pointer, and moves the stack pointer to
make room for locals. On the 8086 that was three instructions:

<!-- block: code -->
PUSH EBP
MOV  EBP, ESP
SUB  ESP, space_for_locals

<!-- block: prose -->
From the 80286 on, one `ENTER` instruction does the same. It was not a win:

<!-- block: quote source="ch-12.md 12.5" -->
saves a few bytes of memory compared with the PUSH, MOV, SUB sequence (4 bytes versus 6 bytes), it actually takes longer to execute (10 clock cycles versus 6 clock cycles).

<!-- block: prose -->
Hold on to that example. It is Stage 13's whole argument (RISC) in miniature: a
complex instruction can cost more than the simple ones it replaces.

### x86: status flags and condition codes

<!-- block: quote source="ch-12.md 12.5" -->
The compare operation in most languages subtracts two operands, as does a subtract operation. The difference is that a compare operation only sets status flags, whereas a subtract operation also stores the result of the subtraction in the destination operand.

<!-- block: callout -->
**The six x86 status flags** (book Table 12.8): **C** carry (or borrow) out of
the leftmost bit · **P** parity of the low byte · **A** auxiliary carry between
half-bytes, for BCD · **Z** zero result · **S** sign of the result · **O**
two's complement overflow.

<!-- block: prose -->
Whether one number is "bigger" depends on how you read the bits, so x86 names the
two comparisons differently: **above/below** for unsigned, **greater/less** for
signed.

<!-- block: code -->
CMP  1111 1111, 0000 0001
unsigned:  255 vs 1   →  above   (JA taken)
signed:     −1 vs 1   →  less    (JL taken, JG not taken)

<!-- block: prose -->
### x86: SIMD and saturation

<!-- block: quote source="ch-12.md 12.5" -->
There are 57 new instructions that treat data in a SIMD (single-instruction, multiple-data) fashion, which makes it possible to perform the same operation, such as addition or multiplication, on multiple data elements at once.

<!-- block: prose -->
MMX packs eight bytes, four 16-bit words or two 32-bit doublewords into one
64-bit operand. Its unusual feature is **saturation arithmetic**:

<!-- block: quote source="ch-12.md 12.5" -->
With saturation arithmetic, if addition results in overflow or subtraction results in underflow, the result is set to the largest or smallest value representable.

<!-- block: code -->
two unsigned 8-bit pixel values:  200 + 100 = 300, which does not fit
wraparound   (ordinary add)       300 − 256 =  44  = 0x2C   a bright pixel turns dark
saturation   (PADDUSB)            clamps to   255  = 0xFF   the brightest value

<!-- block: prose -->
### ARM operation types

ARM's categories are load and store, branch, data processing, multiply,
parallel add and subtract, extend, and status register access. The first one is
the defining choice:

<!-- block: quote source="ch-12.md 12.5" -->
In the ARM architecture, only load and store instructions access memory locations; arithmetic and logical instructions are performed only on registers and immediate values encoded in the instruction.

<!-- block: prose -->
A subroutine call is a **Branch with Link** (`BL`), which keeps the return address
in register LR (R14) instead of on a stack. ARM's four condition flags, **N, Z,
C, V**, mean the same as x86's S, Z, C and O. And unlike x86, the condition is
not only for branches:

<!-- block: quote source="ch-12.md 12.5" -->
All instructions, not just branch instructions, include a condition code field, which means that virtually all instructions may be conditionally executed.

<!-- block: quote source="ch-12.md 12.5" -->
On the other hand, all instructions include 4 bits for the condition code, so there is a trade-off in that fewer bits in the 32-bit instruction are available for opcode and operands.

<!-- block: prose -->
## Endianness: which byte comes first

A 32-bit value occupies four byte addresses. Which byte goes at the lowest one?

<!-- block: quote source="ch-12.md 12A" -->
The mapping on the left stores the most significant byte in the lowest numerical byte address; this is known as big endian and is equivalent to the left-to-right order of writing in Western culture languages. The mapping on the right stores the least significant byte in the lowest numerical byte address; this is known as little endian

<!-- block: prose -->
Our own example: the value **0xCAFEF00D** stored at address 0x200.

<!-- block: code -->
address    big endian    little endian
0x200          CA             0D
0x201          FE             F0
0x202          F0             FE
0x203          0D             CA

<!-- block: prose -->
Both store the same value at the same address; only the byte order inside it
differs. x86 is little endian; IBM System/370, Motorola 680x0, SPARC and most
RISC machines are big endian. Three rules keep it straight:

- Endianness reverses the bytes **inside** one multibyte value.
- It never reorders **separate** items. A character array is stored in the same
  order on both, because each character is its own one-byte item.
- So a block of memory can only be converted from one style to the other if you
  know the data structure in it.

<!-- block: quote source="ch-12.md 12A" -->
The property of endianness does not extend beyond an individual data unit.

<!-- block: prose -->
Neither style wins outright. Big endian makes memory dumps read left to right and
sorts character strings fast; little endian makes higher-precision arithmetic
easier, because the least significant byte is found first.

<!-- block: quote source="ch-12.md 12A" -->
The differences are minor and the choice of endian style is often more a matter of accommodating previous machines than anything else.

<!-- block: prose -->
### Bi-endian

<!-- block: quote source="ch-12.md 12A" -->
The PowerPC is a bi-endian processor that supports both big-endian and littleendian modes. The bi-endian architecture enables software developers to choose either mode when migrating operating systems and applications from other machines.

<!-- block: prose -->
The operating system sets the mode, per process, through bits in the machine
state register. ARM's E-bit, above, is the same idea under program control.

<!-- block: callout -->
**Bits have an order too.** Within a byte, is the first bit numbered 0 or 1, and
is bit 0 the most or the least significant? Machines answer differently, and not
always consistently with their byte order. It matters when you manipulate
individual bits, or send a byte down a serial line one bit at a time.
