<!-- block: brief -->
Stage 10 was about **what** an instruction does. This stage is about **how** it
says it, and it comes down to two questions:

<!-- block: quote source="ch-13.md 13" -->
First, how is the address of an operand specified, and second, how are the bits of an instruction organized to define the operand addresses and operation of that instruction?

<!-- block: prose -->
The first is answered by **addressing modes**, the second by **instruction
formats**. Both are a fight over a small number of bits, and every design you
meet here is one way of losing that fight gracefully.

<!-- block: prose -->
## Why there are addressing modes at all

<!-- block: quote source="ch-13.md 13.1" -->
The address field or fields in a typical instruction format are relatively small. We would like to be able to reference a large range of locations in main memory or, for some systems, virtual memory.

<!-- block: prose -->
If an instruction is 32 bits long and the memory is 4 GB, a plain address would
need all 32 bits and leave nothing for the opcode. So instead of always holding
the address, the address field holds **something from which the address can be
worked out**. Each way of working it out is a mode, and each trades range and
flexibility against extra memory references or extra calculation.

<!-- block: callout -->
**Notation used below** (the book's): **A** is the contents of an address field
in the instruction · **R** is an address field that names a register · **EA** is
the effective address, the actual location of the operand · **(X)** means "the
contents of X".

<!-- block: prose -->
How does the processor know which mode an instruction uses? Either the opcode
implies it, or the instruction carries a **mode field**. And in a machine with
virtual memory (Stage 08), the EA is a virtual address: the MMU maps it to a
physical one, invisibly.

<!-- block: prose -->
## The seven basic modes

### Immediate: the operand is in the instruction

<!-- block: quote source="ch-13.md 13.1" -->
The simplest form of addressing is immediate addressing, in which the operand value is present in the instruction

<!-- block: quote source="ch-13.md 13.1" -->
The advantage of immediate addressing is that no memory reference other than the instruction fetch is required to obtain the operand, thus saving one memory or cache cycle in the instruction cycle. The disadvantage is that the size of the number is restricted to the size of the address field, which, in most instruction sets, is small compared with the word length.

<!-- block: prose -->
An immediate is usually two's complement and is **sign-extended** (Stage 09)
when it is loaded into a full-size register.

### Direct: the field is the address

<!-- block: quote source="ch-13.md 13.1" -->
A very simple form of addressing is direct addressing, in which the address field contains the effective address of the operand:

<!-- block: prose -->
EA = A. One memory reference, no calculation, and a small address space: only
as many locations as the field can count.

### Indirect: the field points at the address

<!-- block: quote source="ch-13.md 13.1" -->
One solution is to have the address field refer to the address of a word in memory, which in turn contains a full-length address of the operand. This is known as indirect addressing:

<!-- block: prose -->
EA = (A). A short field now reaches a whole word's worth of addresses, at a
price:

<!-- block: quote source="ch-13.md 13.1" -->
The disadvantage is that instruction execution requires two memory references to fetch the operand: one to get its address and a second to get its value.

<!-- block: prose -->
### Register: the field names a register

EA = R. A register field is short (3 to 5 bits name 8 to 32 registers) and no
memory reference is needed at all.

<!-- block: quote source="ch-13.md 13.1" -->
The advantages of register addressing are that (1) only a small address field is needed in the instruction, and (2) no time-consuming memory references are required.

<!-- block: prose -->
The catch is that there are few registers, so they only pay off if a value stays
in one for several operations. Deciding which values live in registers is the
programmer's, or the compiler's, job.

### Register indirect: the register holds the address

EA = (R). It is to indirect what register is to direct: the full-width address
sits in a register, so the operand is reached with one memory reference instead
of two.

### Displacement: a register plus a constant

<!-- block: quote source="ch-13.md 13.1" -->
A very powerful mode of addressing combines the capabilities of direct addressing and register indirect addressing.

<!-- block: prose -->
EA = A + (R). The instruction carries a constant A and names a register; their
sum is the address. Three common uses differ only in which part is "the base":

- **Relative (PC-relative).** The register is the program counter, and A is a
  signed offset from the next instruction. Nearby targets need only a few bits.
- **Base-register.** The register holds a base address (the start of a segment,
  Stage 08) and A is a small offset from it.
- **Indexing.** A is the start of a table and the register counts through it.

<!-- block: quote source="ch-13.md 13.1" -->
Relative addressing exploits the concept of locality that was discussed in Chapters 4 and 8. If most memory references are relatively near to the instruction being executed, then the use of relative addressing saves address bits in the instruction.

<!-- block: prose -->
Indexing is what loops are made of, so machines often step the index register
automatically, **autoindexing**. Combine indexing with indirection and the order
matters: **postindexing** is EA = (A) + (R), indexing after the indirection;
**preindexing** is EA = (A + (R)), indexing before it, which is how a multiway
branch table is read.

### Stack: the address is implied

<!-- block: quote source="ch-13.md 13.1" -->
The stack mode of addressing is a form of implied addressing. The machine instructions need not include a memory reference but implicitly operate on the top of the stack.

<!-- block: prose -->
The stack pointer lives in a register, so a stack reference is really register
indirect. That is the zero-address machine from Stage 10.

<!-- block: callout -->
**The seven modes side by side** (book Table 13.1):

| Mode | Algorithm | Advantage | Disadvantage |
|---|---|---|---|
| Immediate | Operand = A | no memory reference | limited operand size |
| Direct | EA = A | simple | limited address space |
| Indirect | EA = (A) | large address space | multiple memory references |
| Register | EA = R | no memory reference | limited address space |
| Register indirect | EA = (R) | large address space | extra memory reference |
| Displacement | EA = A + (R) | flexibility | complexity |
| Stack | EA = top of stack | no memory reference | limited applicability |

<!-- block: prose -->
### One setup, six answers

Our own example. The instruction's address field holds **A = 0x20**, register
**R1 = 0x40**, and memory holds:

<!-- block: code -->
address   contents
0x20      0x50
0x40      0x70
0x50      0x90
0x60      0x11

<!-- block: prose -->
Which operand does each mode deliver, and how many memory references does it
cost after the instruction is fetched?

<!-- block: code -->
mode                EA                      operand   memory refs
immediate           (none)                  0x20      0
direct              A = 0x20                0x50      1
indirect            (A) = (0x20) = 0x50     0x90      2
register            R1                      0x40      0
register indirect   (R1) = 0x40             0x70      1
displacement        A + (R1) = 0x60         0x11      1

<!-- block: prose -->
Six modes, the same two numbers in the instruction, six different operands. That
is why the mode must be known before anything else about the operand.

<!-- block: prose -->
### PC-relative, worked

A 2-byte branch sits at address 0x0100 and its displacement field holds −6. The
PC already points at the next instruction, 0x0102, when the address is formed:

<!-- block: code -->
next instruction   0x0102
+ displacement       −6
= target           0x00FC      (a backward branch, as in a loop)

<!-- block: prose -->
## x86 addressing modes

On the x86 an effective address is an **offset into a segment**. The segment
register selects the segment, its descriptor supplies the segment's start, and
start + offset is the **linear address**, which paging (if on) then translates.
The book sets paging aside here because the instruction set never sees it.

The offset can be built from four parts: a **base register**, an **index
register** scaled by 1, 2, 4 or 8, and a **displacement** of 0, 8 or 32 bits in
the instruction. The modes are the useful combinations of those parts (book
Table 13.2): immediate, register, displacement, base, base with displacement,
scaled index with displacement, base with index and displacement, base with
scaled index and displacement, and relative.

<!-- block: quote source="ch-13.md 13.2" -->
In calculating the effective address, the contents of the index register are multiplied by a scaling factor of 1, 2, 4, or 8, and then added to a displacement. This mode is very convenient for indexing arrays.

<!-- block: prose -->
The scale is the element size. Our own example: an array of 32-bit integers
starts at offset 0x1000 and ESI holds 5. Element 5 is at

<!-- block: code -->
EA = displacement + (ESI) × scale
   = 0x1000       +  5    ×  4
   = 0x1014

<!-- block: prose -->
Base with displacement serves a stack frame (the base register points at the
frame, the displacement picks the local variable) or a record (the base points
at the record, the displacement picks the field). Base with index and
displacement handles a two-dimensional array, one register per dimension.

<!-- block: prose -->
## ARM addressing modes

ARM is a RISC machine, yet its addressing is unusually rich, and it is easiest
to sort by instruction type.

**Load and store** are the only instructions that touch memory, always through
a base register plus an offset, in three variants:

<!-- block: quote source="ch-13.md 13.2" -->
For this addressing method, indexing is not used. An offset value is added to or subtracted from the value in the base register to form the memory address.

<!-- block: quote source="ch-13.md 13.2" -->
The memory address is formed in the same way as for offset addressing. The memory address is also written back to the base register.

<!-- block: quote source="ch-13.md 13.2" -->
The memory address is the base register value. An offset is added to or subtracted from the base register value and the result is written back to the base register.

<!-- block: prose -->
Those are **offset**, **preindex** and **postindex**. Our own example, with r3
holding 0x1000 and an offset of 8:

<!-- block: code -->
instruction             address used    r3 afterwards
LDR r2, [r3, #8]        0x1008          0x1000   offset: r3 untouched
LDR r2, [r3, #8]!       0x1008          0x1008   preindex: add, use, keep
LDR r2, [r3], #8        0x1000          0x1008   postindex: use, then add

<!-- block: prose -->
The `!` marks preindexing. Postindex walks an array one element per load without
a separate add. The offset can also come from a register, shifted on the way in
(**scaled register addressing**).

**Data processing** instructions use registers, or registers and an immediate.
**Branches** use one form only:

<!-- block: quote source="ch-13.md 13.2" -->
The only form of addressing for branch instructions is immediate addressing. The branch instruction contains a 24-bit value. For address calculation, this value is shifted left 2 bits, so that the address is on a word boundary.

<!-- block: prose -->
A 24-bit signed field shifted left 2 is a 26-bit byte offset, which is the ±32 MB
reach you met in Stage 10.

**Load and Store Multiple** move any subset of the 16 registers to or from
consecutive words, named in a 16-bit field with one bit per register. Four modes
choose the direction and timing: increment after, increment before, decrement
after, decrement before. They suit block copies, stacks and procedure exit.

<!-- block: prose -->
## Instruction formats

<!-- block: quote source="ch-13.md 13.3" -->
An instruction format defines the layout of the bits of an instruction, in terms of its constituent fields. An instruction format must include an opcode and, implicitly or explicitly, zero or more operands.

<!-- block: prose -->
### Instruction length

<!-- block: quote source="ch-13.md 13.3" -->
The most obvious trade-off here is between the desire for a powerful instruction repertoire and a need to save space.

<!-- block: prose -->
Programmers want more opcodes, more operands, more modes and more range; all of
them cost bits. But bits are not free:

<!-- block: quote source="ch-13.md 13.3" -->
A 64-bit instruction occupies twice the space of a 32-bit instruction but is probably less than twice as useful.

<!-- block: prose -->
Two more constraints come from the rest of the machine. The instruction length
should equal the memory transfer length, or one should be a multiple of the
other, or a fetch will not bring whole instructions. And since memory is slower
than the processor (Stage 04's whole subject), shorter instructions can be
fetched faster:

<!-- block: quote source="ch-13.md 13.3" -->
Thus, 16-bit instructions can be fetched at twice the rate of 32-bit instructions but probably can be executed less than twice as rapidly.

<!-- block: prose -->
Instruction length should also be a multiple of the character length, usually 8
bits. The book's historical example is IBM moving from a 36-bit architecture to
a 32-bit one for the System/360 so that it could use 8-bit characters.

### Allocation of bits

Once the length is fixed, every bit given to one field is taken from another.

<!-- block: quote source="ch-13.md 13.3" -->
For a given instruction length, there is clearly a trade-off between the number of opcodes and the power of the addressing capability. More opcodes obviously mean more bits in the opcode field. For an instruction format of a given length, this reduces the number of bits available for addressing.

<!-- block: prose -->
Our own example of the budget. A 32-bit instruction with an 8-bit opcode and two
register fields for 32 registers:

<!-- block: code -->
32 bits total
−  8   opcode                 (up to 256 operations)
− 10   two register fields    (5 bits each: 2⁵ = 32 registers)
= 14   left for a displacement or immediate
       as two's complement:   −8192 … +8191

<!-- block: prose -->
Ask for 64 registers and each register field grows by a bit; the displacement
shrinks to 12 bits, −2048 to +2047. That is the trade-off in numbers. The book
lists the factors that decide how the addressing bits are spent:

<!-- block: callout -->
**What decides the addressing bits** (book §13.3): the **number of addressing
modes** (implicit, or explicit mode bits) · the **number of operands** (two is
typical today) · **register versus memory** operands (a register needs only a
few bits) · the **number of register sets** (two sets of eight need only 3 bits
per reference) · the **address range** · and the **address granularity** (byte
addressing needs more bits than word addressing for the same memory).

<!-- block: prose -->
A **variable-length opcode** is one escape: short opcodes for instructions that
need many address bits, longer ones for instructions that need few.

### Four historical machines, four answers

- **PDP-8:** a 12-bit instruction, one accumulator, a 3-bit opcode. It stays
  flexible with a page bit and an indirect bit, and opcode 7 turns the rest of
  the word into bit-per-operation **microinstructions**.
- **PDP-10:** a 36-bit fixed format with a 9-bit opcode and an 18-bit address
  field, built for ease of programming over economy of space.
- **PDP-11:** a 16-bit minicomputer with thirteen formats; every operand carries
  its own 3-bit mode and 3-bit register, so any mode works with any opcode.
- **VAX:** a 1- or 2-byte opcode followed by zero to six operand specifiers, up
  to 37 bytes, so every instruction can have its "natural" number of operands.

<!-- block: quote source="ch-13.md 13.3" -->
The PDP-8 instruction format is remarkably efficient. It supports indirect addressing, displacement addressing, and indexing.

<!-- block: quote source="ch-13.md 13.3" -->
It eases the task of the programmer or compiler at the expense of an inefficient utilization of space. This was a conscious choice made by the designers and therefore cannot be faulted as poor design.

<!-- block: prose -->
That second quotation is about the PDP-10, and it is the attitude to take to all
four: each design is a deliberate choice of what to make cheap.

The PDP-11 introduced a word you will need:

<!-- block: quote source="ch-13.md 13.3" -->
One advantage of linking the addressing mode to the operand rather than the opcode, as is sometimes done, is that any addressing mode can be used with any opcode. As was mentioned, this independence is referred to as orthogonality.

<!-- block: prose -->
### Variable-length instructions

<!-- block: quote source="ch-13.md 13.3" -->
The principal price to pay for variable-length instructions is an increase in the complexity of the processor.

<!-- block: prose -->
They buy a large repertoire and flexible addressing in compact code. Because the
processor does not know how long the next instruction is, it typically fetches
at least as many bytes as the longest possible one.

<!-- block: prose -->
## x86 instruction format

Only the opcode is always there. Everything else is optional:

<!-- block: quote source="ch-13.md 13.4" -->
Instructions are made up of from zero to four optional instruction prefixes, a 1- or 2-byte opcode, an optional address specifier (which consists of the ModR/M byte and the Scale Index Base byte) an optional displacement, and an optional immediate field.

<!-- block: callout -->
**The x86 fields, in order** (book Figure 13.9):

| Field | Size | What it does |
|---|---|---|
| Prefixes | 0 to 4 bytes | LOCK or a repeat prefix; segment override; operand size; address size |
| Opcode | 1 to 3 bytes | the operation, plus bits for data size, direction and sign extension |
| ModR/M | 0 or 1 byte | register or memory operand, and the addressing mode |
| SIB | 0 or 1 byte | scale, index and base, for the scaled modes |
| Displacement | 0, 1, 2 or 4 bytes | a signed displacement |
| Immediate | 0, 1, 2 or 4 bytes | an immediate operand |

<!-- block: quote source="ch-13.md 13.4" -->
The Mod field (2 bits) combines with the R/M field to form 32 possible values: 8 registers and 24 indexing modes; the Reg/Opcode field (3 bits) specifies either a register number or three more bits of opcode information

<!-- block: prose -->
The addressing mode lives in the opcode sequence, not with each operand:

<!-- block: quote source="ch-13.md 13.4" -->
Because only one operand can have address-mode information, only one memory operand can be referenced in an instruction.

<!-- block: prose -->
The VAX, carrying a mode with every operand, can do memory-to-memory in one
instruction; the x86 cannot, but its instructions are more compact. The
complexity of the encoding comes partly from backward compatibility with the
8086, partly from trying to help compiler writers in every possible way.

<!-- block: prose -->
## ARM instruction format

<!-- block: quote source="ch-13.md 13.4" -->
All instructions in the ARM architecture are 32 bits long and follow a regular format (Figure 13.10). The first four bits of an instruction are the condition code.

<!-- block: quote source="ch-13.md 13.4" -->
The next three bits specify the general type of instruction. For most instructions other than branch instructions, the next five bits constitute an opcode and/or modifier bits for the operation. The remaining 20 bits are for operand addressing. The regular structure of the instruction formats eases the job of the instruction decode units.

<!-- block: prose -->
### Immediate constants by rotation

A 32-bit instruction cannot hold a 32-bit constant, so ARM stores an 8-bit value
and a 4-bit rotate:

<!-- block: quote source="ch-13.md 13.4" -->
The 8-bit immediate value is expanded to 32 bits and then rotated right by a number of bits equal to twice the 4-bit rotate value.

<!-- block: code -->
8-bit value   rotate field   rotate right by   constant
0xFF          0              0                 0x000000FF
0xFF          4              8                 0xFF000000
0x3F          15             30                0x000000FC   (30 right = 2 left)
0x01          1              2                 0x40000000

<!-- block: prose -->
Twelve bits cannot name every 32-bit value, but they name the constants programs
use most: small numbers, and single bytes at any even bit position.

### Thumb and Thumb-2

<!-- block: quote source="ch-13.md 13.4" -->
The Thumb instruction set is a re-encoded subset of the ARM instruction set.

<!-- block: prose -->
Thumb instructions are 16 bits, half of ARM's 32. The book accounts for the 16
saved bits: 5 from dropping the condition field and the update-flags bit, 2 from
a smaller opcode and type field, and 9 from smaller operand fields (only r0 to r7,
3 bits each, and no rotate on immediates). 5 + 2 + 9 = 16.

<!-- block: quote source="ch-13.md 13.4" -->
It introduces 32-bit instructions that can be intermixed freely with the older 16-bit Thumb instructions.

<!-- block: prose -->
That is Thumb-2, which ended the choice between Thumb for size and ARM for
speed. In the book's figures, Thumb-2 code was 26% smaller than ARM when
compiled for performance and ran at 98% of ARM's performance.

<!-- block: prose -->
## Machine language and assembly language

<!-- block: quote source="ch-13.md 13.5" -->
A processor can understand and execute machine instructions. Such instructions are simply binary numbers stored in the computer.

<!-- block: prose -->
The book's example computes N = I + J + K and climbs four rungs (its Figure
13.14). In **binary**, every word is typed as bits. In **hexadecimal**, the same
words are shorter to type but just as opaque. A **symbolic** program writes each
opcode as a mnemonic (`LDA`, `ADD`, `STA`) but still gives every word an
absolute address, so inserting one line moves every address after it. The last
rung replaces addresses with **names**:

<!-- block: quote source="ch-13.md 13.5" -->
With this last refinement, we have an assembly language. Programs written in assembly language (assembly programs) are translated into machine language by an assembler. This program must not only do the symbolic translation discussed earlier but also assign some form of memory addresses to symbolic addresses.

<!-- block: prose -->
So the distinction you need is this: **machine language** is the binary the
processor executes; **assembly language** is a symbolic notation for it, with
mnemonics and symbolic addresses, that an assembler translates one instruction
at a time.

<!-- block: quote source="ch-13.md 13.5" -->
The development of assembly language was a major milestone in the evolution of computer technology. It was the first step to the high-level languages in use today.
