<!-- block: brief -->
One hour, one distinction.

Everything else in CPE 412 — eighteen chapters of caches, pipelines, addressing
modes and microcode — is an answer to a question this chapter teaches you to
ask: **is this something the programmer can see, or something the engineer chose
underneath?**

Get that wrong and the rest of the course blurs into one undifferentiated pile
of hardware facts. Get it right and every chapter has a place to sit.

<!-- block: prose -->
## The one distinction

Two terms get used almost interchangeably in conversation, and they are not the
same thing. The textbook draws the line like this:

<!-- block: quote source="ch-01.md 1.1" -->
Computer architecture refers to those attributes of a system visible to a programmer or, put another way, those attributes that have a direct impact on the logical execution of a program.

<!-- block: quote source="ch-01.md 1.1" -->
Computer organization refers to the operational units and their interconnections that realize the architectural specifications.

<!-- block: prose -->
Read those twice, because the second half of each sentence is where the work is.

**Architecture is a contract.** It is what a program is allowed to depend on: the
instruction set, how many bits an integer has, how memory is addressed, what
happens to the registers when an instruction executes. The term you will see
used for this contract is **instruction set architecture (ISA)**.

**Organization is how that contract is honoured.** Control signals, the bus
between the processor and memory, the memory technology, whether there is a
cache and how big it is. None of that appears in the contract. All of it decides
whether the machine is fast or slow, cheap or expensive, hot or cool.

<!-- block: callout -->
**The example to remember.** Stallings puts the whole distinction in one pair of
sentences, and it is worth memorising because you can re-derive the definitions
from it:

> it is an architectural design issue whether a computer will have a multiply instruction. It is an organizational issue whether that instruction will be implemented by a special multiply unit or by a mechanism that makes repeated use of the add unit of the system.

*Does `MUL` exist?* — architecture. *Is there a real multiplier behind it, or a
loop that adds?* — organization. Same program, same answer, different silicon,
different speed.

<!-- block: prose -->
## Why anyone cares

This is not a vocabulary exercise. The distinction is what lets a company sell
you a slow machine today and a fast one in three years **without breaking the
software you already own.**

Keep the architecture fixed and vary the organization, and you get a *family* of
machines: same instruction set, different price and performance. IBM's
System/370 is the textbook case — introduced in 1970, still recognisable in
IBM's mainframe line decades later, with the organization replaced underneath it
many times over.

That is also the reason your x86 laptop runs software compiled before it was
built, and why an ARM phone and an ARM tablet with wildly different internals
run the same app.

<!-- block: callout -->
**Where the line blurs.** In microcomputers the two move together — a change in
technology drives new organization *and* new architecture, because there is less
pressure to stay compatible generation to generation. The clearest example is
the reduced instruction set computer, which you meet in **Stage 13**: an
argument that started as an organizational observation and ended up rewriting
the architecture.

<!-- block: prose -->
## A computer is a hierarchy

A modern processor holds billions of transistors. Nobody understands it as
billions of transistors. The way anyone understands a system this size is the
same way you understand a company or a city:

<!-- block: quote source="ch-01.md 1.2" -->
A hierarchical system is a set of interrelated subsystems, each of the latter, in turn, hierarchical in structure until we reach some lowest level of elementary subsystem.

<!-- block: prose -->
At every level you ask only two questions, and the book names them:

- **Structure** — the way in which the components are interrelated.
- **Function** — the operation of each individual component as part of the structure.

The point of a hierarchy is that **each level only needs a simplified picture of
the level below.** You can reason about the CPU without thinking about
transistors, the same way you can reason about a function without thinking about
the compiler.

This course descends that hierarchy deliberately, top down, and the map you use
to navigate it is the same shape. Watch where each stage sits.

<!-- block: prose -->
## Function: only four things

Whatever a computer is doing — rendering a game, routing a packet, running
payroll — it is doing some combination of exactly four things:

- **Data processing** — the actual computation. The forms data takes are endless; the fundamental types of processing are few.
- **Data storage** — even data passing straight through has to sit somewhere for a moment. That is short-term storage. Files that outlive the program are long-term storage.
- **Data movement** — between the computer and the world. Directly attached, that is **input–output (I/O)** and the thing on the other end is a **peripheral**. Over distance, it is **data communications**.
- **Control** — a control unit manages the computer's resources and directs the other three in response to instructions.

<!-- block: prose -->
## The sequences those four functions allow

Because there are four functions, there is a small, countable set of things a
computer operation can *be* — and every program you will ever write is a long
sequence drawn from it:

1. **Move data from one place to another.** Nothing is computed. Copying a
   buffer, reading a key, sending a byte to the screen.
2. **Store data, or retrieve stored data.** Movement where one end is memory.
3. **Process data in storage** — read it, compute on it, put the result back.
   The archetypal `LOAD` / operate / `STORE`.
4. **Process data on the way to or from I/O** — compute as it moves, rather than
   storing it first.

That is the complete list. Everything else is these four, sequenced.

## Structure: only four parts

At the top level, a traditional single-processor computer has four structural
components:

- **Central processing unit (CPU)** — controls the operation of the computer and performs its data processing functions; often simply referred to as processor.
- **Main memory** — stores data.
- **I/O** — moves data between the computer and its external environment.
- **System interconnection** — some mechanism that provides for communication among CPU, main memory, and I/O. The common example is a **system bus**: a set of conducting wires everything else attaches to.

Notice these are the four *functions* again, wearing hardware. Processing, storage,
movement, and the thing that connects them. That correspondence is not a
coincidence, and it is the single most useful thing to carry out of this hour.

Open the CPU and the pattern repeats:

- **Control unit** — controls the operation of the CPU and hence the computer.
- **Arithmetic and logic unit (ALU)** — performs the computer's data processing functions.
- **Registers** — provides storage internal to the CPU.
- **CPU interconnection** — some mechanism that provides for communication among the control unit, ALU, and registers.

Control, processing, storage, interconnection — one level down, the same four.
**Stage 12** takes this apart properly; **Stages 15 and 16** open the control
unit itself.

<!-- block: callout -->
**Say these precisely, because the industry does not.** The 10th edition pins
the modern terms down, and you will be marked on using them correctly:

- **CPU** — the portion that fetches and executes instructions: an ALU, a control unit, and registers.
- **Core** — an individual processing unit on a processor chip.
- **Processor** — a physical piece of silicon containing one or more cores. More than one, and it is a **multicore processor**.

So "a quad-core processor" is one piece of silicon with four cores on it — not
four processors. **Stage 17** is about what happens when you have several.

## What to take into Stage 02

One question, asked of everything you meet for the rest of the semester:

> **Is this visible to the program, or is it a choice underneath?**

Cache — organization; a program cannot see it, only feel it. Addressing modes —
architecture; a program is written in terms of them. Pipelining — organization.
Number of registers — architecture.

Stage 02 asks the immediate follow-up: if organization is where the speed
decisions live, **how do you measure whether one was any good?**
