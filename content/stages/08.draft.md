<!-- block: brief -->
Stage 07 freed the processor from waiting on a device: interrupts and DMA let
it **do something else** while the transfer happens. This chapter answers the
question that leaves behind. *Something else* means another program — so who
keeps several programs in memory at once, decides which one runs next, and
stops them from trampling each other?

That is the operating system. This course is about hardware, so we look at the
two OS jobs the hardware was built to support: **scheduling** the processor and
**managing memory**. Every mechanism here — the timer interrupt, privileged
instructions, the page table, the TLB — is a piece of hardware that exists
because an operating system asked for it.

<!-- block: prose -->
## What an operating system is for

<!-- block: quote source="ch-08.md 8.1" -->
An OS is a program that controls the execution of application programs and acts as an interface between applications and the computer hardware.

<!-- block: prose -->
Read that twice, because it holds a strange idea. The OS *controls* the
processor, yet it is itself just a program **the processor runs**. It cannot
supervise from outside like a thermostat watching a heater. It has to hand the
processor over to your program, and then rely on the hardware — an interrupt,
a timer, a service call — to give it back.

Keep that picture in mind for the whole chapter: the OS is always either
*running* or *waiting to be let back in*, and the hardware decides when it gets
back in.

<!-- block: prose -->
## How operating systems grew up

Each stage of this history exists to stop the processor sitting idle, and each
one needed a new piece of hardware to make it safe.

### Serial processing — no OS at all

In the earliest machines a programmer booked the computer on a sign-up sheet,
loaded a program from cards, and watched the lights. Two things wasted time:
a booking ran over or ended early, and every job had to be set up by hand —
compiler loaded, tapes mounted — before it could start.

### Simple batch systems — a monitor takes the queue

<!-- block: quote source="ch-08.md 8.1" -->
With such a system, also called a monitor, the user no longer has direct access to the processor. Rather, the user submits the job on cards or tape to a computer operator, who batches the jobs together sequentially and places the entire batch on an input device, for use by the monitor.

<!-- block: prose -->
The monitor runs a job, gets control back when the job ends, and starts the
next one immediately. The idle gaps between bookings disappear.

But a monitor that hands the processor to user programs needs protection from
them, and that protection is hardware:

- **Memory protection**, so a user program cannot overwrite the monitor.
- **A timer**, so one job cannot keep the processor forever.
- **Privileged instructions**, so only the monitor can do I/O.
- **Interrupts**, so control can come back to the monitor at all.

Those four appear again in every operating system you will ever use.

<!-- block: prose -->
### Multiprogrammed batch systems — never wait for I/O

A batch monitor still left the processor idle whenever the running job waited
for a device. The book's worked figure on a record-processing job is blunt about
how much that costs:

In this example the computer spends over 96% of its time waiting for I/O devices to finish transferring data!

<!-- block: prose -->
The cure is to keep more than one program in memory, and switch to another one
whenever the current one has to wait.

<!-- block: quote source="ch-08.md 8.1" -->
Furthermore, we might expand memory to hold three, four, or more programs and switch among all of them (Figure 8.5c). This technique is known as multiprogramming, or multitasking.

<!-- block: prose -->
Notice what this depends on: **interrupt-driven I/O and DMA from Stage 07.**
If the processor had to poll the device, it could not leave to run anything
else. Multiprogramming is what those mechanisms were for.

### Time-sharing systems — many people at once

<!-- block: quote source="ch-08.md 8.1" -->
Just as multiprogramming allows the processor to handle multiple batch jobs at a time, multiprogramming can be used to handle multiple interactive jobs. In this latter case, the technique is referred to as time sharing, because the processor's time is shared among multiple users.

<!-- block: callout -->
**Same mechanism, different goal.** Batch multiprogramming tries to keep the
**processor** busy. Time sharing tries to keep the **response time** short for
the people at the terminals. The machinery is identical; what the scheduler is
trying to optimise is not.

<!-- block: prose -->
## Scheduling: three decisions at three speeds

Once several programs share the machine, something has to decide who runs. The
OS makes that decision at three different time scales. First, a word: a
*process* is a program in execution — the thing the processor is actually given.

### Long-term: who gets in

<!-- block: quote source="ch-08.md 8.2" -->
The long-term scheduler determines which programs are admitted to the system for processing. Thus, it controls the degree of multiprogramming (number of processes in memory).

<!-- block: prose -->
Admit too few and the processor idles; admit too many and every process gets a
sliver of a crowded memory. It runs rarely — when a job arrives or one ends.

### Medium-term: who stays in memory

<!-- block: quote source="ch-08.md 8.2" -->
Medium-term scheduling is part of the swapping function, described in Section 8.3.

<!-- block: prose -->
When every process in memory is blocked waiting for I/O, the OS can **swap**
one out to disk and bring another in. The medium-term decision is which ones
are in main memory at all.

### Short-term: who runs next

<!-- block: quote source="ch-08.md 8.2" -->
The short-term scheduler, also known as the dispatcher, executes frequently and makes the fine-grained decision of which job to execute next.

<!-- block: callout -->
**One way to remember the three.** Long-term is the door into the building.
Medium-term is who is allowed in the room. Short-term is who holds the
microphone right now. They run at very different rates: the dispatcher may run
many times a second, the long-term scheduler only when a job arrives or leaves.

<!-- block: prose -->
### What the dispatcher works with

Every process moves through a small set of **states**: new, ready, running,
blocked (waiting for an event such as I/O) and exited. The dispatcher only ever
chooses among the *ready* ones.

<!-- block: figure id="08-process-states" after="8.7" -->
The five-state process model, with the event that moves a process along each
arrow. Ready and Running are highlighted: they are the two the dispatcher moves
a process between.

<!-- block: prose -->

To stop a process and resume it later without it noticing, the OS keeps a
**process control block** for each one: its identifier, state, priority,
program counter, memory pointers and the saved register contents — the
*context*. Switching processes is exactly Stage 03's interrupt sequence, with
the saved state going into the control block.

<!-- block: code -->
process A running
    ├─ A requests I/O        (or a timer interrupt, or a device interrupt)
    ├─ save A's PC + registers  → A's control block, state = blocked
    ├─ dispatcher picks B from the ready queue
    └─ restore B's PC + registers ← B's control block, state = running
process B running

## Memory management: sharing one memory among many processes

<!-- block: quote source="ch-08.md 8.3" -->
In a multiprogramming system, the "user" part of memory is subdivided to accommodate multiple processes. The task of subdivision is carried out dynamically by the OS and is known as memory management.

<!-- block: prose -->
Multiprogramming only pays if enough processes are in memory that at least one
is usually ready. So memory has to be packed tightly — and a process cannot know
in advance *where* in memory it will land.

### Partitioning, and why it wastes memory

The simplest scheme carves memory into **fixed partitions**. Make them all the
same size and a small process wastes most of its partition; make them unequal
sizes and you still waste the gap between what a process needs and the
partition it gets. That waste *inside* an allocation is **internal
fragmentation**.

**Dynamic partitions** give each process exactly what it asks for. That starts
well, but as processes come and go they leave holes between them, too small for
anything — **external fragmentation**.

<!-- block: quote source="ch-08.md 8.3" -->
One technique for overcoming this problem is compaction: From time to time, the OS shifts the processes in memory to place all the free memory together in one block.

<!-- block: prose -->
Compaction works, but moving whole processes around costs processor time — and
it raises the problem that unlocks everything else in this chapter.

### Logical and physical addresses

If a process can be loaded anywhere, and even moved while it runs, the
addresses inside its instructions cannot be real memory locations.

<!-- block: quote source="ch-08.md 8.3" -->
A logical address is expressed as a location relative to the beginning of the program. Instructions in the program contain only logical addresses.

<!-- block: prose -->
The **processor hardware** turns each logical address into a physical one as
the instruction executes. In the simplest scheme it just adds the process's
current base address. Move the process, change the base register, and every
address in it is still right.

<!-- block: prose -->
## Paging

Partitions are wasteful because a process needs one *contiguous* region. Paging
removes that requirement.

<!-- block: quote source="ch-08.md 8.3" -->
Then the chunks of a program, known as pages, could be assigned to available chunks of memory, known as frames, or page frames. At most, then, the wasted space in memory for that process is a fraction of the last page.

<!-- block: prose -->
A process's pages can sit in **any** free frames, in any order. The OS keeps a
**page table** per process saying which frame holds each page, and the hardware
splits every logical address into a page number and an offset.

<!-- block: code -->
page size = 1 KB = 1024 bytes
logical address 1502
    page   = 1502 div 1024 = 1
    offset = 1502 mod 1024 = 478
page table: page 1 → frame 13
physical address = 13 × 1024 + 478 = 13790

<!-- block: figure id="08-paging-translation" -->
The same translation drawn: the page number goes through the page table, and the
offset is copied across unchanged.

<!-- block: callout -->
**Why page sizes are powers of two.** With 1024-byte pages, "div 1024" and
"mod 1024" are not arithmetic at all — the offset is simply the low 10 bits of
the address and the page number is the rest. The hardware splits the address
by wiring, not by dividing. You will see the same trick in Stage 09.

<!-- block: prose -->
## Virtual memory

Paging lets a process be scattered. One more step lets it be **incomplete**.

<!-- block: quote source="ch-08.md 8.3" -->
That refinement is demand paging, which simply means that each page of a process is brought in only when it is needed, that is, on demand.

<!-- block: prose -->
Most of a program sits unused at any moment — the principle of locality from
Stage 04 again. So load only the pages being used. When the program touches a
page that is not in memory, the hardware raises a **page fault**, and the OS
fetches the page from disk.

The consequence is remarkable: a process no longer has to fit in main memory at
all. That is the definition this chapter asks you for.

<!-- block: quote source="ch-08.md 8.3" -->
Because a process executes only in main memory, that memory is referred to as real memory. But a programmer or user perceives a much larger memory—that which is allocated on the disk. This latter is therefore referred to as virtual memory.

<!-- block: prose -->
The cost: when a page comes in, another must go out. Choose badly and you evict
a page that is needed a moment later.

<!-- block: quote source="ch-08.md 8.3" -->
Too much of this leads to a condition known as thrashing: the processor spends most of its time swapping pages rather than executing instructions.

<!-- block: prose -->
### The translation lookaside buffer

Every memory reference now needs a page-table lookup first — and the page table
is itself in memory, so each access could cost **two** memory accesses.

<!-- block: quote source="ch-08.md 8.3" -->
To overcome this problem, most virtual memory schemes make use of a special cache for page table entries, usually called a translation lookaside buffer (TLB).

<!-- block: callout -->
**It is Stage 04 all over again.** The TLB is a cache, its hit rate depends on
locality, and a miss falls back to the slower structure behind it. A single
memory reference can now pass through the TLB, the page table, the data cache,
main memory and — on a page fault — the disk.

<!-- block: prose -->
## Segmentation, and how it compares with paging

<!-- block: quote source="ch-08.md 8.3" -->
Whereas paging is invisible to the programmer and serves the purpose of providing the programmer with a larger address space, segmentation is usually visible to the programmer and is provided as a convenience for organizing programs and data and as a means for associating privilege and protection attributes with instructions and data.

<!-- block: prose -->
A **segment** is a variable-sized, named region: the code, a table, a stack that
grows. Addresses become *(segment, offset)*. Because a segment is a meaningful
unit, it is natural to share it, protect it, or let it grow.

<!-- block: callout -->
**Paging versus segmentation — the assessment the syllabus asks for.**

| | Paging | Segmentation |
|---|---|---|
| Unit size | fixed, small | variable, as large as the data |
| Visible to the programmer | no | yes |
| Fragmentation | internal, at most part of the last page | external, holes between segments |
| Good at | packing memory efficiently, virtual memory | sharing, protection, growing structures |

Each is strong exactly where the other is weak.

<!-- block: quote source="ch-08.md 8.3" -->
These advantages are not available with paging, which is invisible to the programmer. On the other hand, we have seen that paging provides for an efficient form of memory management. To combine the advantages of both, some systems are equipped with the hardware and OS software to provide both.

<!-- block: prose -->
## Two real machines

**Intel x86** does both. A program's address goes through **segmentation**
first, producing a linear address, and then through two-level **paging** — a
page directory pointing to page tables — to reach physical memory. Either stage
can be switched off, giving four different views of memory. Segments also carry
one of four **privilege levels**, so the most trusted part of the OS runs at
level 0 and applications usually at level 3.

**ARM** uses paging only, with a memory-management unit that walks one or two
levels of translation tables. Besides small and large pages it can map whole
1-MB **sections** with a single entry, which saves TLB space for big regions —
an embedded designer's trade-off.
