<!-- block: brief -->
Stage 06 ended on a number: a disk takes about **4 milliseconds** to reach a
block, and a processor cycle is well under a nanosecond. Waiting means throwing
away millions of cycles per access.

This chapter is the three ways to not wait, in increasing order of how much
hardware you are willing to spend. It is the most directly useful hour in the
first half of the course, because the same three shapes appear everywhere a fast
thing talks to a slow one.

<!-- block: prose -->
## The I/O module, and why it exists

A processor cannot talk to a disk directly. The speeds differ by six orders of
magnitude, the data formats differ, the electrical characteristics differ, and
there are dozens of device types with nothing in common.

So an **I/O module** sits between them. It presents the processor with a uniform
interface — a set of registers to read and write — and deals with the device's
actual peculiarities on the other side.

That is an abstraction boundary in exactly Stage 01's sense: the processor sees
an *architecture* (registers, commands, status bits) and the module owns the
*organization* behind it.

<!-- block: prose -->
## Three techniques, and the whole chapter is choosing between them

<!-- block: quote source="ch-07.md 7.3" -->
Three techniques are possible for I/O operations. With programmed I/O, data are exchanged between the processor and the I/O module. The processor executes a program that gives it direct control of the I/O operation, including sensing device status, sending a read or write command, and transferring the data. When the processor issues a command to the I/O module, it must wait until the I/O operation is complete.

<!-- block: prose -->
### 1. Programmed I/O — the processor asks, repeatedly

The processor issues a command and then **polls** the status register in a loop
until the device says it is finished.

<!-- block: quote source="ch-07.md 7.4" -->
The I/O module takes no further action to alert the processor. In particular, it does not interrupt the processor.

<!-- block: code -->
issue command
loop:
    read status register
    if not ready: goto loop      ← millions of wasted cycles
    transfer one word
    if more data: goto loop

<!-- block: prose -->
Simple, and catastrophically wasteful. The processor burns its entire capacity
asking "are you done yet?" — and for a 4 ms disk access at 1 GHz, that is around
**four million iterations of a loop that does nothing.**

It is still the right answer sometimes: when the wait is genuinely shorter than
the cost of switching away, polling wins. That is a real trade, not a
consolation.

<!-- block: prose -->
### 2. Interrupt-driven I/O — the device speaks up

The processor issues the command and **goes away and does something else**. When
the device is ready it raises an interrupt; the processor saves its state, runs
the handler to transfer the data, and resumes.

This is the mechanism from Stage 03, put to work.

<!-- block: code -->
issue command
... run other work ...           ← the four million cycles are USEFUL now
    ┌─ INTERRUPT
    ├─ save state
    ├─ transfer one word
    └─ restore state, resume

<!-- block: prose -->
The waiting is gone. But look closely at what remains: **the processor still
transfers every single word**, and each transfer carries the cost of saving and
restoring state. Move a 4 KB block a word at a time and you have paid that
overhead a thousand times.

<!-- block: prose -->
### 3. Direct memory access — take the processor out of the path

A **DMA module** is given a command, a memory address and a count, and then
moves the data *itself*, straight between the device and memory. The processor
is interrupted **once**, when the whole transfer is done.

<!-- block: code -->
tell the DMA module: read | address | 4096 bytes
... run other work ...
    ┌─ ONE INTERRUPT — the whole block has arrived
    └─ resume

<!-- block: prose -->
The cost is that the DMA module and the processor now contend for the memory
bus. DMA steals cycles from the processor when both want memory at once — hence
**cycle stealing**. That is a real slowdown, and it is still overwhelmingly
cheaper than a thousand interrupts.

<!-- block: callout -->
**The progression is one idea applied three times.**

| | Who waits | Who moves the data | Interrupts per block |
|---|---|---|---|
| Programmed | Processor | Processor | none |
| Interrupt-driven | Nobody | Processor | one per word |
| DMA | Nobody | DMA module | one per block |

Each step **removes the processor from more of the work.** Follow that arrow one
step further and the module gets its own instruction set — which is exactly what
an I/O channel is.

<!-- block: prose -->
## I/O channels and processors

An **I/O channel** is a DMA module that executes a *program* of I/O
instructions, held in main memory, without the processor's involvement. The
processor says "run this channel program" and is told when the whole sequence is
finished — not one block, but a whole choreography of them.

An **I/O processor** goes further and has local memory of its own; it is a small
computer devoted to moving data.

This is the same pattern as Stage 02's multicore answer, arriving from a
different direction: when one processor cannot keep up, **add a specialised one
rather than a faster one.**

<!-- block: prose -->
## Two external interfaces worth knowing

**Thunderbolt** carries PCI Express and DisplayPort over one cable, so a single
connector supplies both data and display bandwidth. Its point is not raw speed
but **convergence**: fewer distinct buses to design around.

**InfiniBand** is a switched-fabric interconnect for servers and clusters —
high throughput, very low latency, and designed so that many nodes communicate
simultaneously rather than contending for a shared medium.

<!-- block: callout -->
**Notice InfiniBand's shape.** Switched, point-to-point, many simultaneous
conversations — the bus's problems from Stage 03, solved the same way PCIe
solved them, at the scale of a whole machine room.

That scale is what **Stage 18** is about.

## What to carry into Stage 08

You can now say which of the three techniques a situation calls for, and defend
it by naming the cost you are avoiding and the cost you are accepting.

Stage 08 asks the question that follows immediately: if the processor is free to
do other work while a device is busy, **who decides what that other work is?**
That is an operating system, and scheduling is the subject of the project.
