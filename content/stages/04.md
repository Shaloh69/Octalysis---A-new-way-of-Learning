<!-- block: brief -->
In Stage 02 you computed a CPI of 2.24, and **0.80 of it came from cache
misses** — over a third of the total, from 10% of the instructions.

This chapter is what to do about that. It is the most arithmetic-heavy hour of
the course so far, and the numbers you produce here are the ones that show up in
the Prelim.

<!-- block: prose -->
## The problem, stated as a trade

There are three things you want from memory: **fast**, **large**, and **cheap**.
You can have any two.

- Fast and cheap → small (registers, SRAM)
- Large and cheap → slow (disk)
- Fast and large → ruinously expensive

The hierarchy is the engineering answer to a trade you cannot win outright:

<!-- block: code -->
             ┌──────────────┐   faster, smaller,
             │  Registers   │   more expensive per bit
             ├──────────────┤        ▲
             │  L1 cache    │        │
             ├──────────────┤        │
             │  L2 / L3     │        │
             ├──────────────┤        │
             │ Main memory  │        │
             ├──────────────┤        │
             │  Disk / SSD  │        ▼
             └──────────────┘   larger, cheaper, slower

<!-- block: prose -->
And here is the definition to know exactly:

<!-- block: quote source="ch-04.md 4.2" -->
Cache memory is designed to combine the memory access time of expensive, highspeed memory combined with the large memory size of less expensive, lower-speed memory.

<!-- block: prose -->
## Why it works at all: locality

A cache would be useless if programs touched memory at random. They do not, and
the reason has a name:

<!-- block: quote source="ch-04.md 4.3" -->
the principle of locality, which states that data in the vicinity of a referenced word are likely to be referenced in the near future.

<!-- block: prose -->
Two flavours, both true of nearly all real code:

- **Temporal locality** — a word used now is likely to be used again soon. Loop
  counters, the top of the stack.
- **Spatial locality** — a word near one just used is likely to be next. Array
  traversal, sequential instructions.

This is why a cache fetches a whole **block**, not a single word. You paid the
latency; you may as well bring the neighbours.

<!-- block: prose -->
## The arithmetic you must be able to do

**Hit ratio.** The fraction of accesses found in cache:

<!-- block: code -->
H = hits / (hits + misses)

<!-- block: prose -->
**Average memory access time.** The number that actually matters, because it is
what feeds back into CPI:

<!-- block: code -->
T_avg = H × T_cache  +  (1 − H) × T_main

<!-- block: prose -->
**Worked example.** Cache access 2 ns, main memory 60 ns, hit ratio 0.95:

<!-- block: code -->
T_avg = 0.95 × 2  +  0.05 × 60
      = 1.9 + 3.0
      = 4.9 ns

<!-- block: callout -->
**Look at the split.** The 5% of accesses that miss contribute **3.0 of the
4.9 ns** — more than the 95% that hit. Raise the hit ratio to 0.98 and the
average drops to 3.16 ns, a 35% improvement from a 3-point change.

**Misses dominate.** That asymmetry is the entire reason cache design is worth
a chapter, and it is why "just add more cache" is not automatically the answer —
what matters is whether the extra cache raises H.

<!-- block: prose -->
## Splitting an address

A cache does not store addresses whole. It splits each one into fields, and
which fields depend on the mapping.

**Direct mapped** — every block of main memory has exactly one line it may
occupy:

<!-- block: code -->
┌─────────┬───────┬──────┐
│   TAG   │ LINE  │ WORD │
└─────────┴───────┴──────┘

WORD = log₂(bytes per line)
LINE = log₂(number of lines)
TAG  = whatever is left

<!-- block: prose -->
**Worked example.** A 64 KB cache, 16-byte lines, 24-bit addresses:

<!-- block: code -->
Lines = 64 KB / 16 B = 4096 lines

WORD = log₂ 16   = 4 bits
LINE = log₂ 4096 = 12 bits
TAG  = 24 − 12 − 4 = 8 bits

┌──────────┬──────────────┬────────┐
│ TAG  (8) │  LINE  (12)  │ W  (4) │
└──────────┴──────────────┴────────┘

<!-- block: prose -->
Direct mapping is cheap — one comparison — but brittle. Two hot blocks that map
to the same line evict each other on every access, however empty the rest of the
cache is. That is **thrashing**, and it is why the other two mappings exist.

**Fully associative** — a block may go in any line. No LINE field at all, so the
tag is everything above the word offset. Flexible, and expensive: every tag must
be compared at once.

**Set associative** — the compromise, and what real caches use. The cache is
divided into sets; a block maps to one *set* and may occupy any line within it.

<!-- block: code -->
┌─────────┬───────┬──────┐
│   TAG   │  SET  │ WORD │
└─────────┴───────┴──────┘

Same 64 KB cache, 16-byte lines, 4-way set associative:

Lines = 4096, so sets = 4096 / 4 = 1024

WORD = 4 bits
SET  = log₂ 1024 = 10 bits
TAG  = 24 − 10 − 4 = 10 bits

<!-- block: callout -->
**Notice the tag grew.** Fewer set bits means more tag bits, which means more
SRAM spent on tags rather than data. Associativity is not free — you are trading
storage and comparator count for a lower miss rate, and past about 8-way the
trade stops paying.

<!-- block: prose -->
## Replacement: which line goes

Once a set is full, something must be evicted. The syllabus names four, and you
must be able to trace each by hand:

- **LRU** — least recently used. Best hit rate of the four in practice, because
  it is a direct bet on temporal locality. Costs the most to implement: you must
  track *order of use*.
- **LFU** — least frequently used. Counts accesses. Vulnerable to a block that
  was hot long ago and has a high count it no longer deserves.
- **FIFO** — oldest first. Trivially cheap, ignores usage entirely.
- **Random** — pick one. Sounds absurd; performs surprisingly close to LRU, and
  costs nothing.

<!-- block: prose -->
**Trace them.** Four-line set, reference string `1 2 3 4 1 2 5 1 2 3 4 5`:

<!-- block: code -->
FIFO
ref: 1  2  3  4  1  2  5  1  2  3  4  5
     M  M  M  M  H  H  M  H  H  M  M  M
                          evict 1 → 5
     hits: 4    misses: 8

LRU
ref: 1  2  3  4  1  2  5  1  2  3  4  5
     M  M  M  M  H  H  M  H  H  M  M  M
     hits: 4    misses: 8

<!-- block: prose -->
On this string they tie — which is itself the lesson. **A replacement policy is
only as good as the access pattern it meets**, and defending a choice means
naming the pattern. That is exactly what the project asks of you.

<!-- block: prose -->
## Write policy, line size, and how many caches

**Write-through** updates cache and memory together — simple, correct, and
generates a lot of memory traffic. **Write-back** updates only the cache and
marks the line dirty, writing it out on eviction — far less traffic, and now
memory is temporarily *wrong*, which matters enormously the moment there is more
than one core. **Stage 17** is where that bill arrives.

**Line size** has an optimum rather than a direction. Bigger lines exploit
spatial locality — until they do not:

<!-- block: quote source="ch-04.md 4.3" -->
The hit ratio will begin to decrease, however, as the block becomes even bigger and the probability of using the newly fetched information becomes less than the probability of reusing the information that has to be replaced.

<!-- block: prose -->
**How many caches.** Modern designs use several levels — L1 closest and
smallest, L2 and L3 progressively larger and slower — and often split L1 into
separate instruction and data caches, because fetch and operand access have
different patterns and would otherwise evict each other.
