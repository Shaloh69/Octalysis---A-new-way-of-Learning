<!-- block: brief -->
Stages 10 and 11 described the instruction set from the outside: what an
instruction says and how its bits are laid out. This stage opens the processor
that carries it out. You will meet its registers, follow the instruction cycle
register by register, and then see the idea that makes every modern processor
fast: **pipelining**, overlapping the stages of one instruction with the stages
of the next, and the hazards that stop that overlap from being free.

<!-- block: prose -->
## What a processor must do

<!-- block: quote source="ch-14.md 14.1" -->
The processor reads an instruction from memory (register, cache, main memory).

<!-- block: prose -->
That is the first of five jobs: **fetch** the instruction, **interpret** it,
**fetch data** it needs, **process** the data, and **write** the results. To do
them the processor needs somewhere to keep things for a moment:

<!-- block: quote source="ch-14.md 14.1" -->
It must remember the location of the last instruction so that it can know where to get the next instruction. It needs to store instructions and data temporarily while an instruction is being executed. In other words, the processor needs a small internal memory.

<!-- block: prose -->
So the processor is three things joined by an internal bus: the **ALU**, the
**control unit**, and that small internal memory, the **registers**. The book
points out the echo: the whole computer is processor, memory and I/O joined by
a bus, and the processor is the same pattern one level down.

<!-- block: prose -->
## Register organization

Registers are the top of Stage 04's memory hierarchy, above cache: the fastest,
smallest and most expensive storage there is. They play two roles.

<!-- block: quote source="ch-14.md 14.2" -->
Enable the machine-or assembly language programmer to minimize main memory references by optimizing use of registers.

<!-- block: quote source="ch-14.md 14.2" -->
Used by the control unit to control the operation of the processor and by privileged, operating system programs to control the execution of programs.

<!-- block: prose -->
The first are **user-visible registers**, the second **control and status
registers**. The line between them is not clean: the program counter is user
visible on the x86 and hidden on many other machines.

### User-visible registers

<!-- block: quote source="ch-14.md 14.2" -->
A user-visible register is one that may be referenced by means of the machine language that the processor executes.

<!-- block: prose -->
They fall into four categories:

- **General purpose:** usable for any operand of any opcode, at least in
  principle. Often there are exceptions, such as dedicated floating-point or
  stack registers.
- **Data:** may hold data only, and cannot be used to calculate an address.
- **Address:** devoted to addressing, such as **segment pointers**, **index
  registers** (Stage 11's indexing) and the **stack pointer**.
- **Condition codes (flags):** bits the hardware sets as a result of operations.

<!-- block: quote source="ch-14.md 14.2" -->
Condition codes are bits set by the processor hardware as the result of operations.

<!-- block: quote source="ch-14.md 14.2" -->
Generally, machine instructions allow these bits to be read by implicit reference, but the programmer cannot alter them.

<!-- block: prose -->
Three design questions follow. **General or specialised?** Specialised registers
save bits, because the opcode implies which set a specifier means, but they
limit the programmer. **How many?** The book's answer:

<!-- block: quote source="ch-14.md 14.2" -->
As we previously discussed, somewhere between 8 and 32 registers appears optimum [LUND77]. Fewer registers result in more memory references; more registers do not noticeably reduce memory references (e.g., see [WILL90]).

<!-- block: prose -->
(Stage 13 meets the RISC exception: hundreds of registers.) **How long?** An
address register must hold the largest address, and a data register most data
types; some machines pair two registers for double-length values.

Not every machine uses condition codes. IA-64 and MIPS make their branches
compare and decide in one instruction instead. The book's Table 14.1 weighs it
up: condition codes save COMPARE and TEST instructions and allow multiway
branches, but they add complexity and, in a pipeline, need special
synchronization.

### Control and status registers

<!-- block: quote source="ch-14.md 14.2" -->
Four registers are essential to instruction execution:

<!-- block: callout -->
**The four essential registers** (book §14.2):

| Register | Holds |
|---|---|
| Program counter (PC) | the address of an instruction to be fetched |
| Instruction register (IR) | the instruction most recently fetched |
| Memory address register (MAR) | the address of a location in memory |
| Memory buffer register (MBR) | a word to be written to memory, or the word most recently read |

<!-- block: quote source="ch-14.md 14.2" -->
In a bus-organized system, the MAR connects directly to the address bus, and the MBR connects directly to the data bus.

<!-- block: prose -->
Most processors also keep a **program status word (PSW)**: the condition codes
plus status such as the **interrupt enable/disable** bit and the **supervisor**
bit.

<!-- block: quote source="ch-14.md 14.2" -->
Indicates whether the processor is executing in supervisor or user mode. Certain privileged instructions can be executed only in supervisor mode, and certain areas of memory can be accessed only in supervisor mode.

<!-- block: prose -->
That one bit is what makes Stage 08's protection possible. Other control
registers you may meet: an interrupt vector register, a system stack pointer,
and a page table pointer for virtual memory.

### Two 16-bit designs, two philosophies

The book compares two processors of the same era. The **Motorola MC68000**
splits its 32-bit registers into eight data and nine address registers, a
regular design that saves one bit per register specifier. The **Intel 8086**
makes every register special purpose: a multiply always uses the accumulator,
string instructions use their pointer registers implicitly. Compact code,
less flexibility.

<!-- block: quote source="ch-14.md 14.2" -->
There is no universally accepted philosophy concerning the best way to organize processor registers [TOON81].

<!-- block: prose -->
The 80386 then shows a third force: to keep running 8086 programs, it embedded
the old 16-bit registers inside its new 32-bit ones (AX is the low half of EAX).
Backward compatibility limits every later design.

<!-- block: prose -->
## The instruction cycle, in full

Stage 03 gave you fetch, execute and interrupt. This stage adds one more:

<!-- block: quote source="ch-14.md 14.3" -->
After an instruction is fetched, it is examined to determine if any indirect addressing is involved. If so, the required operands are fetched using indirect addressing. Following execution, an interrupt may be processed before the next instruction fetch.

<!-- block: prose -->
That is the **indirect cycle**, and it exists because of Stage 11: an indirect
operand needs an extra memory read to fetch its address.

### Data flow, register by register

<!-- block: quote source="ch-14.md 14.3" -->
The PC contains the address of the next instruction to be fetched. This address is moved to the MAR and placed on the address bus. The control unit requests a memory read, and the result is placed on the data bus and copied into the MBR and then moved to the IR. Meanwhile, the PC is incremented by 1, preparatory for the next fetch.

<!-- block: prose -->
Our own trace, starting with PC = 0x0300:

<!-- block: code -->
fetch      MAR ← PC              MAR = 0x0300   (onto the address bus)
           memory read           MBR ← the word at 0x0300 (from the data bus)
           IR  ← MBR             IR holds the instruction
           PC  ← PC + 1          PC = 0x0301
indirect   MAR ← address field   (only if IR's operand is indirect)
           memory read           MBR ← the operand's address
execute    depends on the opcode in IR
interrupt  MBR ← PC, MAR ← save location, memory write, PC ← handler address

<!-- block: quote source="ch-14.md 14.3" -->
The fetch and indirect cycles are simple and predictable. The execute cycle takes many forms; the form depends on which of the various machine instructions is in the IR.

<!-- block: quote source="ch-14.md 14.3" -->
The current contents of the PC must be saved so that the processor can resume normal activity after the interrupt.

<!-- block: prose -->
## Instruction pipelining

<!-- block: quote source="ch-14.md 14.4" -->
Instruction pipelining is similar to the use of an assembly line in a manufacturing plant. An assembly line takes advantage of the fact that a product goes through various stages of production. By laying the production process out in an assembly line, products at various stages can be worked on simultaneously.

<!-- block: prose -->
### Two stages first

Split the cycle into fetch and execute. While one instruction executes, the
fetch stage uses the idle memory to fetch the next one:

<!-- block: quote source="ch-14.md 14.4" -->
This is called instruction prefetch or fetch overlap.

<!-- block: prose -->
If the two stages took equal time, the instruction rate would double. It does
not, for two reasons the book gives: execution usually takes longer than fetch,
so the fetch stage waits; and a **conditional branch** leaves the next address
unknown until it executes. The simple guess is to fetch the next instruction in
sequence anyway: if the branch is not taken, nothing is lost; if it is taken,
the fetched instruction is thrown away.

### Six stages

More stages, each shorter, give more overlap. The book's decomposition:

<!-- block: callout -->
**The six-stage pipeline** (book §14.4): **FI** fetch instruction · **DI**
decode instruction · **CO** calculate operands (effective addresses) · **FO**
fetch operands · **EI** execute instruction · **WO** write operand.

<!-- block: prose -->
With equal stages, the arithmetic is simple. Nine instructions of six time units
each would take 54 units one after another; overlapped, a new one starts every
unit, and the ninth finishes at time 14.

<!-- block: figure id="12-pipeline-timing" after="14.10" -->
Nine instructions through the six stages, one stage per time unit, each starting
one unit after the last. The execute stage is highlighted. The last instruction
finishes at time 14.

<!-- block: prose -->
That count assumes every stage takes the same time, every instruction uses all
six stages, and the memory stages (FI, FO, WO) never conflict. Real pipelines
fall short of all three, and two more things break the flow: a **conditional
branch** that is taken, and an **interrupt**.

In the book's example, instruction 3 branches to instruction 15. The pipeline
has already started instructions 4 to 7; when instruction 3 executes and the
branch is taken, those four are flushed, instruction 15 starts from FI, and no
instruction completes for four time units. That gap is the **branch penalty**.

<!-- block: figure id="12-branch-penalty" after="14.11" -->
The same pipeline when instruction 3 is a taken branch to instruction 15. The
dashed cells were fetched and then discarded, and no instruction finishes in
time units 9 to 12.

<!-- block: prose -->
### Pipeline performance

The **cycle time** τ is the time to move every instruction one stage forward:
the slowest stage's delay plus the delay of the latch between stages. For a
k-stage pipeline running n instructions with no branches:

<!-- block: quote source="ch-14.md 14.4" -->
A total of k cycles are required to complete the execution of the first instruction, and the remaining n - 1 instructions require n - 1 cycles.

<!-- block: code -->
T(k,n) = [k + (n − 1)] τ                    time for n instructions
S(k)   = n·k / [k + (n − 1)]                speedup over no pipeline (kτ each)

<!-- block: prose -->
Our own numbers. Four stages with delays 10, 8, 12 and 9 ns and a 1 ns latch;
ten instructions:

<!-- block: code -->
τ       = max(10, 8, 12, 9) + 1  = 13 ns          the slowest stage sets the pace
T(4,10) = [4 + 9] × 13 ns        = 169 ns         13 cycles
S(4)    = 10 × 4 / 13            ≈ 3.08           not 4: filling the pipe costs k − 1 cycles
S(6) for n = 100: 600 / 105      ≈ 5.71           close to 6 once n is large

<!-- block: prose -->
As n grows the speedup approaches k, so more stages look better. They are not
free. The potential gains of additional

<!-- block: quote source="ch-14.md 14.4" -->
pipeline stages are countered by increases in cost, delays between stages, and the fact that branches will be encountered requiring the flushing of the pipeline.

<!-- block: prose -->
Each stage boundary adds latch overhead, and the control logic that tracks
dependencies grows enormously with the number of stages.

<!-- block: prose -->
## Pipeline hazards

<!-- block: quote source="ch-14.md 14.4" -->
A pipeline hazard occurs when the pipeline, or some portion of the pipeline, must stall because conditions do not permit continued execution. Such a pipeline stall is also referred to as a pipeline bubble.

<!-- block: prose -->
There are three kinds: **resource**, **data** and **control**.

### Resource (structural) hazards

<!-- block: quote source="ch-14.md 14.4" -->
A resource hazard occurs when two (or more) instructions that are already in the pipeline need the same resource. The result is that the instructions must be executed in serial rather than parallel for a portion of the pipeline.

<!-- block: prose -->
The book's example: memory with a single port. If instruction 1 reads its
operand from memory in the same cycle that instruction 3 wants to be fetched,
the fetch waits one cycle. Another is two instructions ready to execute and one
ALU. The cure is more of the resource: more memory ports, more ALUs.

### Data hazards

<!-- block: quote source="ch-14.md 14.4" -->
A data hazard occurs when there is a conflict in the access of an operand location.

<!-- block: prose -->
The book's x86 example:

<!-- block: code -->
ADD EAX, EBX     EAX ← EAX + EBX
SUB ECX, EAX     ECX ← ECX − EAX     needs the new EAX

<!-- block: quote source="ch-14.md 14.4" -->
The ADD instruction does not update register EAX until the end of stage 5, which occurs at clock cycle 5. But the SUB instruction needs that value at the beginning of its stage 2, which occurs at clock cycle 4. To maintain correct operation, the pipeline must stall for two clocks cycles.

<!-- block: prose -->
The three types are named by the order of the two accesses:

<!-- block: callout -->
**The three data hazards** (book §14.4):

| Hazard | Also called | The conflict |
|---|---|---|
| Read after write (RAW) | true dependency | a later instruction reads before an earlier write completes |
| Write after read (WAR) | antidependency | a later write completes before an earlier read |
| Write after write (WAW) | output dependency | two writes complete in the wrong order |

<!-- block: prose -->
Our own sequence, to classify:

<!-- block: code -->
I1  ADD R1, R2, R3     R1 ← R2 + R3
I2  SUB R4, R1, R5     R4 ← R1 − R5
I3  MOV R2, R6         R2 ← R6
I4  ADD R4, R7, R8     R4 ← R7 + R8

I1 → I2   RAW on R1   I2 reads what I1 writes
I1 → I3   WAR on R2   I3 writes what I1 reads
I2 → I4   WAW on R4   both write R4; I4's value must be the one left

<!-- block: prose -->
In a simple in-order pipeline only RAW actually bites. WAR and WAW matter once
instructions can complete out of order, which is Stage 14.

### Control hazards

<!-- block: quote source="ch-14.md 14.4" -->
A control hazard, also known as a branch hazard, occurs when the pipeline makes the wrong decision on a branch prediction and therefore brings instructions into the pipeline that must subsequently be discarded.

<!-- block: prose -->
## Dealing with branches

<!-- block: quote source="ch-14.md 14.4" -->
Until the instruction is actually executed, it is impossible to determine whether the branch will be taken or not.

<!-- block: prose -->
The book surveys five approaches:

- **Multiple streams.** Fetch down both paths at once with duplicated pipeline
  front ends. It costs contention, and a second branch needs yet another stream.
- **Prefetch branch target.** Fetch the target as well as the next instruction,
  and keep it until the branch decides.
- **Loop buffer.** A small, very fast memory holding the most recently fetched
  instructions. A short loop runs from the buffer after its first pass.
- **Branch prediction.** Guess, and fetch down the guessed path.
- **Delayed branch.** Rearrange the program so useful instructions follow the
  branch (Stage 13).

<!-- block: quote source="ch-14.md 14.4" -->
The loop buffer is similar in principle to a cache dedicated to instructions. The differences are that the loop buffer only retains instructions in sequence and is much smaller in size and hence lower in cost.

<!-- block: prose -->
### Branch prediction

<!-- block: quote source="ch-14.md 14.4" -->
The first three approaches are static: they do not depend on the execution history up to the time of the conditional branch instruction. The latter two approaches are dynamic: They depend on the execution history.

<!-- block: prose -->
The three static ones are **predict never taken**, **predict always taken** and
**predict by opcode**; the two dynamic ones are the **taken/not taken switch**
(history bits) and the **branch history table**.

A one-bit history has a weakness the book names: a loop branch is almost always
taken, yet one bit mispredicts twice per loop, on the exit and again on the
next entry. Two bits fix it:

<!-- block: quote source="ch-14.md 14.4" -->
Thus, the algorithm requires two consecutive wrong predictions to change the prediction decision.

<!-- block: prose -->
Our own trace: a loop branch that is taken three times and then falls through,
run twice. Both predictors start out predicting taken.

<!-- block: code -->
actual          T   T   T   N   T   T   T   N
1-bit predicts  T   T   T   T   N   T   T   T      (it predicts the last outcome)
                ✓   ✓   ✓   ✗   ✗   ✓   ✓   ✗      3 misses
2-bit predicts  T   T   T   T   T   T   T   T      (one miss is not enough to flip it)
                ✓   ✓   ✓   ✗   ✓   ✓   ✓   ✗      2 misses

<!-- block: prose -->
The **branch history table** goes further: a small cache, beside the fetch
stage, whose entries hold a branch's address, its history bits, and its target,
so the target can be fetched as soon as the prediction is made.

<!-- block: prose -->
### The Intel 80486 pipeline

A real example with five stages: **Fetch** (into two 16-byte prefetch buffers),
**Decode 1** (opcode and addressing mode, from the first 3 bytes), **Decode 2**
(control signals, and the harder address calculations), **Execute**, and
**Write back**.

<!-- block: quote source="ch-14.md 14.4" -->
With the use of two decode stages, the pipeline can sustain a throughput of close to one instruction per clock cycle. Complex instructions and conditional branches can slow down this rate.

<!-- block: prose -->
It also shows **bypassing**: when a value loaded into a register is needed as
the next instruction's base register, signal paths let D2 take the value WB is
writing, saving a stage, so the stall is one cycle instead of more.

## The x86 processor

<!-- block: callout -->
**x86 registers, 32-bit integer unit** (book Table 14.2): **8 general** (32 bits;
sixteen 64-bit ones in 64-bit mode) · **6 segment** (16 bits; CS for code, SS for
the stack, DS, ES, FS and GS for data) · **EFLAGS** (32 bits; RFLAGS, 64, in
64-bit mode) · the **instruction pointer**. The floating-point unit adds eight
80-bit numeric registers used as a stack, plus control, status and tag word.

<!-- block: prose -->
**EFLAGS** holds the six condition codes from Stage 10 plus control bits such as
the **trap flag** (an interrupt after every instruction, for debugging), the
**interrupt enable flag**, and the **direction flag** for string instructions.
**Control registers** CR0 to CR4 hold system-wide modes: CR0's **PE** bit enables
protected mode and its **PG** bit enables paging, after which CR3 locates the
page directory (Stage 08).

The MMX registers are a lesson in reuse:

<!-- block: quote source="ch-14.md 14.5" -->
In fact, the processor does not include specific MMX registers. Rather, the processor uses an aliasing technique

The existing floating-point registers are used to store MMX values.

<!-- block: prose -->
### Interrupts and exceptions on the x86

<!-- block: quote source="ch-14.md 14.5" -->
An interrupt is generated by a signal from hardware, and it may occur at random times during the execution of a program. An exception is generated from software, and it is provoked by the execution of an instruction.

<!-- block: prose -->
Interrupts are **maskable** (the INTR pin, ignored unless IF is set) or
**nonmaskable** (the NMI pin). Exceptions are **processor-detected** (an error
executing an instruction, such as a divide error or page fault) or
**programmed** (INT, INTO, INT3, BOUND). Each type has a number indexing a
256-entry **interrupt vector table**. On an interrupt the processor uses the
stack:

<!-- block: quote source="ch-14.md 14.5" -->
2. The current value of the EFLAGS register is pushed onto the stack.
3. Both the interrupt (IF) and trap (TF) flags are cleared. This disables INTR interrupts and the trap or single-step feature.
4. The current code segment (CS) pointer and the current instruction pointer (IP or EIP) are pushed onto the stack.

<!-- block: prose -->
(Before those, the stack segment and pointer are pushed if the privilege level
changes; after them, an error code if there is one; then the vector is loaded
into CS and EIP.) An **IRET** restores everything that was pushed.

## The ARM processor

ARM is mainly RISC, with a moderate number of uniform registers, load/store
data processing, fixed-length instructions (32 bits, or 16 in Thumb), a separate
shifter that can preprocess an operand, and conditional execution. Of that last
one, the book says conditional

<!-- block: quote source="ch-14.md 14.6" -->
execution of instructions minimizes the need for conditional branch instructions, thereby improving pipeline efficiency, because pipeline flushing is reduced.

<!-- block: prose -->
That sentence ties ARM back to this stage: fewer branches, fewer flushes.

### Processor modes

<!-- block: quote source="ch-14.md 14.6" -->
The ARM architecture supports seven execution modes. Most application programs execute in user mode.

<!-- block: prose -->
The other six are privileged. Five are **exception modes**, entered by an
exception: **supervisor** (the OS, entered by a software interrupt), **abort**
(memory faults), **undefined** (an unknown instruction), **fast interrupt**
(FIQ) and **interrupt** (IRQ). The sixth, **system** mode, runs privileged OS
tasks with the user registers.

### Banked registers

<!-- block: quote source="ch-14.md 14.6" -->
Registers are arranged in partially overlapping banks, with the current processor mode determining which bank is available. At any time, sixteen numbered registers and one or two program status registers are visible, for a total of 17 or 18 software-visible registers.

<!-- block: prose -->
ARM has 37 32-bit registers in all: 31 general purpose and 6 program status
registers. R0 to R7, R15 (the PC) and the **CPSR** are shared by every mode.
Each exception mode has its own **R13** (stack pointer) and **R14** (link
register) and a **saved program status register (SPSR)**; fast interrupt mode
also has its own R8 to R12. The point is speed: an exception switches banks
instead of saving registers to memory, and a fast interrupt has enough private
registers to need almost no saving at all.

On an exception, the CPSR is copied to the mode's SPSR and the return address
goes into the mode's R14; returning moves SPSR back to CPSR and R14 into the
PC.

## What to carry into Stage 13

You can now sort a machine's registers into user-visible and control/status and
say what each is for, trace the fetch, indirect, execute and interrupt cycles
through PC, MAR, MBR and IR, compute pipeline time and speedup, classify a
hazard as resource, data (RAW, WAR, WAW) or control, and compare the ways of
